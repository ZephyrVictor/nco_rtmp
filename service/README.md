# NCO 监考服务运维手册

本服务把“直播监考 / 服务器辅助录像”和“宿主机本地 MKV 原件”分开管理。自动检查参数、哈希和完整解码，不自动证明全屏采集、无暂停或覆盖实际比赛。

## 访问与账号

- 服务器部署目录：`/data/2027nco/service`；数据根目录：`/data/2027nco`。
- 管理入口：`https://10.77.0.1:18443`，限组织方 WireGuard 专网。
- SSH 隧道：`ssh -N -L 18443:127.0.0.1:18443 ncoai@202.112.51.208`，然后访问 `https://127.0.0.1:18443`。
- 初始账号：`admin`；初始密码文件：`service/secrets/admin_password`，权限 0600。登录后可自行修改密码，修改会注销全部旧会话，初始文件不会同步新密码。
- 选手账号绑定唯一选手；选手只能上传、查看和下载自己的原件。监考员可观看、审核和确认告警；名单、账号、场次由管理员维护。

目前使用本部署签发的私有 CA，公钥文件为 `tls/ca.crt`。尚未提供正式域名和证书；组织方应采用受管理终端信任的证书，或由管理员分发私有 CA。没有自动修改本机钥匙串或系统信任。私有 CA 密钥在 `secrets/tls/ca.key`，不挂入网关。

HTTP 18080 只重定向到 HTTPS 18443。多画面依赖 HTTP/2，不能退回单个站点的 HTTP/1.1，否则浏览器通常只允许 6 条并发长连接。API、SRS HTTP 接口、上传后端不对公网发布端口。

## 规则与客户端

根据提供的 ICO 2026 PDF §11.3 和附录：

| 项目 | 设置 |
| --- | --- |
| 采集 | 宿主机，一个完整显示器采集源；无裁切、遮挡或暂停 |
| 画布 | 与显示器原生分辨率一致 |
| 输出 | 保持屏幕比例，至少 1280×720 |
| 帧率 | 整数 1 FPS |
| 输出模式 / 容器 | Advanced / MKV |
| 录制视频 | x264 / CRF 24 / High |
| 录制音频 | FFmpeg AAC / 44100 Hz / Mono |
| 连续时长 | 两天分别完整录制每场 7 小时 |
| 故障 | 立即通报志愿者，尽快恢复，提交全部原件和异常记录 |

网页“设置”可下载 OBS profile。它不选择物理显示器，也不自动授权操作系统采集权限。必须另外选择本地可写录制目录，并检查采集源和成片。当前 Mac 的配置为原生画布 2560×1664，等比例输出 1280×832，profile 名为 ICO2026，本地目录 `~/Movies/ICO2026`。

直播使用独立编码输出，配置包中为 x264 High、CBR 900 kbps、zerolatency、2 秒关键帧，AAC 96 kbps，约 1 Mbps 总码率。先现场检查小字可读性，再在 0.5–1 Mbps 范围调整辅助直播。本地原件仍使用 CRF 24，不能改为固定码率来限制直播流量。直播也用 1 FPS，避免改动本地录制的规则帧率。直接把含 B 帧的测试 MKV 循环转推时出现过播放器起播超时，不作为已验收的直播编码方式。

推流入口为 `rtmp://10.77.0.1:1935/live`；每人使用管理界面生成的独立密钥和正确场次。密钥仅显示一次，数据库只保存哈希。重置须在离线时进行。Mac 通过 SSH 测试时可另建 `-L 11935:10.77.0.1:1935`，将 OBS 测试推流服务器设为 `rtmp://127.0.0.1:11935/live`。

## 部署与更新

新部署依次执行：

```sh
python3 bootstrap.py
python3 setup_tls.py
cd web
npm ci
npm run build
cd ..
docker compose config --quiet
docker compose build api
docker compose up -d
docker compose ps
```

基础镜像和依赖已固定版本。UID/GID 1001 须拥有数据目录和 secrets；在其他机器部署时需调整。不要清理共享服务器的 Docker 镜像、卷或其他业务。

更新前先做一致性数据库备份并保留旧镜像 ID，再同步代码、构建和重建 API / worker / gateway。比赛期间不要升级 SRS 或更改场次。新的源目录保留旧 `conf`、`html`、`scripts` 和历史 `recordings`，运行的是本目录 compose。

## 日常检查

1. 导入正式选手 CSV，列为 `id,name,group`；创建绑定账号，发放推流凭据。
2. 配置两天场次开始时间。界面按操作者本地时区显示，数据库用 Unix UTC，导出清单使用显式 UTC。开始时间未设置时不生成“比赛中缺席”告警。
3. 每台宿主机做 10–15 分钟实际全屏录制，确认屏幕四边、终端文字、音频、文件增长及断网后本地录制继续。
4. 赛前提前录制和推流；监考页面每页 16 路，翻页会销毁旧播放器，放大复用原播放器。
5. 发现断流、数据停滞、DVR 不增长或监控进程失联，现场立即核查并通报，随后在告警中填写处理记录。界面确认不会代替向志愿者实际通报，系统没有配置外部短信或消息通知。
6. 赛后选手上传本地 MKV 原件。浏览器先计算 SHA-256；同一账号重新选择同一文件可断点续传。完成后服务器保留原件、核对 SHA-256、读取参数并完整解码。
7. 原件参数无问题仍需人工核对真实比赛时间覆盖、宿主机完整采集、暂停和异常记录。短片、CBR、损坏文件和哈希错误不会被标记合规。

服务器 DVR 为 300 秒左右 FLV 分片，仅是辅助副本；FLV 不依赖 MP4 的末尾索引，意外中断时仍可逐标签读取已写入的数据。历史 MP4 保留；断流或等待关键帧会改变分片长度。回调和扫描补录入库，原片不自动合并或转码。重启遗留的临时文件在离线且至少 60 秒未写入后送检、告警，不会伪装成完整录像。时间覆盖未知时保留空值，不用分片时长之和伪造连续覆盖。

## 容量与资源

- 初始赛事逻辑预算：6 TiB；单次上传上限 32 GiB，全局上传连接最多 16，每个源 IP 最多 4。
- 物理空余不足 100 GiB、使用率达 90% 或预算不足时拒绝新上传。已排定比赛期间暂停新上传；已开始的上传可继续，应在开赛前完成或暂停。
- 磁盘 80 / 85 / 90% 告警。共享 `/data` 的其他业务也会改变空余量，6 TiB 不是内核文件系统配额。
- SRS 最大连接数 2048，文件描述符 8192；SRS 最多 4 CPU / 2 GiB，API 2 CPU / 512 MiB，校验进程最多 8 CPU / 4 GiB、6 个并行任务。解码线程受限，重启后恢复持久化队列，反复被中断三次的任务转人工处理。
- 接收预算暂按 400 Mbps，设计目标 200 路 × 0.5–1 Mbps 与 64 路观看。服务器 Docker 网络压测不证明真实赛场、公网、WireGuard 路径或客户端解码承载能力。
- 不自动删除原件。损坏文件、错误哈希、失败报告和测试证据均保留。保留期由赛事负责人确定。

## 监控

已有 Prometheus 新增 `nco-proctor` 采集任务，原有 postgres / node / redis 任务保留。指标入口仅绑定 Docker 私网宿主地址 `172.17.0.1:19185/metrics`，需要 Bearer token；凭据在 `secrets/metrics_token`，不在网页代码中。

`grafana-dashboard.json` 为可导入仪表盘，尚未通过 Grafana 管理账号安装。告警中心已展示服务、磁盘、直播、录像和原件异常。没有独立备份时持续显示未配置告警。

```sh
docker compose ps
docker compose logs --tail=100 api worker srs tusd gateway
docker compose exec -T api python -m app.cli health
docker compose exec -T worker python -m app.cli health --worker
```

不要公开原始日志；SRS 拒绝非法请求时可能记录请求参数。已关闭常规 INFO 推流日志并限制日志轮转。

## 备份与恢复

每日在 `metadata-backups` 生成通过 SQLite integrity_check 的一致性快照；同一 RAID 的快照和 DVR 都不是独立备份。独立存储目的地尚未提供，因此当前没有完成全量独立备份和容灾验收。

准备另一台存储或不同设备上的挂载点，将其挂入一次性备份容器后执行：

```sh
docker compose run --rm --no-deps -v /mnt/independent:/backup api \
  python -m app.cli backup --destination /backup
```

程序拒绝与 DATA 相同文件系统的目标，复制已计算哈希的全部原件，核对目标 SHA-256，再导出一致性数据库和清单；它不会自动备份 DVR。网络盘还需人工确认不是原 RAID 的回环导出。执行后 UI 记录验证时间，超过 24 小时未更新重新告警。备份应由组织方配置定时运行并监测结果，保留多代版本。

恢复前停止 API 和 worker，并备份现存数据库及 WAL/SHM 文件。将已验完整性的 SQLite 快照恢复为 `metadata/proctor.sqlite3`，恢复对应清单中的原件和上传数据，再启动服务。已停服且已备份的旧 WAL/SHM 文件不能与旧数据库快照混用。先在隔离目录做恢复演练，再替换生产数据。

本次故障验收会将一份新元数据快照复制到 Mac，在独立 SQLite 中检查完整性及最新上传回执；这只验证元数据恢复流程，不代表全部赛事原件已独立备份。

## 验收与回退

```sh
docker compose run --rm --no-deps -v /data/2027nco/service/tests:/suite:ro api python /suite/integration.py
docker compose run --rm --no-deps load-test
```

负载测试创建独立 LOAD 前缀、使用合成源，默认 10+4 / 50+16 / 200+64 / 260+84 分级短测，结束后停用测试选手，保存每阶段 JSON 和辅助录像。测试不适合在正式比赛期间运行。压测进程最多 4 CPU / 2 GiB。

7 小时服务端演练命令如下，按 200 路和 64 路观看持续运行并保存结果。它不能代替真实宿主机 OBS 全屏录制和现场网络演练：

```sh
docker compose run --rm --no-deps -e 'LOAD_STAGES=[[200,64,25200]]' load-test
```

正式上线前仍须完成真实赛场网络与全程演练、每台 OBS 采集验收、独立存储备份恢复、受信任证书、值班与通报责任人确认。短测通过不是完整赛事合规认证。

原始服务配置备份：`/data/2027nco-backups/pre-optimization-20261019-1143/config.tar.gz`。如需回退，先停止本服务，再恢复配置并检查端口绑定；不得自动重启原先无鉴权的公网配置。回退时保留所有 `originals`、`uploads`、`dvr`、`metadata` 和历史 `recordings`。本地 OBS 录制独立继续。
